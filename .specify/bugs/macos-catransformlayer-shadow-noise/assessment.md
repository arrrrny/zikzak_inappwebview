# Bug Assessment: macOS `CATransformLayer … shadow* will have no effect` flood

- **Slug**: macos-catransformlayer-shadow-noise
- **Created**: 2026-08-24
- **Source**: pasted text (runtime console from `flutter run -d macos` of the zuraffa_browser demo)
- **Verdict**: invalid (out of scope — Flutter framework console noise, not a zikzak_inappwebview defect)
- **Severity**: low

## Report (verbatim or summarized)

Hundreds of lines like this on every window/compositing pass:

```
2026-08-24 17:33:32.365 zuraffa_browser[71079:6490487] <CATransformLayer: 0x600003670ba0> - changing property shadowOffset in transform-only layer, will have no effect
2026-08-24 17:33:32.365 zuraffa_browser[71079:6490487] <CATransformLayer: 0x600003670ba0> - changing property shadowColor in transform-only layer, will have no effect
2026-08-24 17:33:32.365 zuraffa_browser[71079:6490487] <CATransformLayer: 0x600003670ba0> - changing property shadowRadius in transform-only layer, will have no effect
```

The pattern repeats for many distinct `CATransformLayer` addresses (one per
Material widget that carries elevation: `AppBar`, `InputChip`, etc.).

## Symptom

macOS Core Animation logs a warning for every `shadow*` property set on a
`CATransformLayer` (transform-only layers ignore shadows). This is emitted by
Flutter's macOS embedder while compositing the **Flutter-owned** Material
widgets in the demo's UI (the `AppBar` and the `InputChip` tab strip), NOT by
the `InAppWebView` native view. The app renders and behaves correctly; the
messages are pure console noise.

This is the well-known Flutter-on-macOS cosmetic warning (a transform-only
layer cannot show a shadow, so the engine logs and drops it). It reproduces in
any Flutter macOS app that uses elevated Material widgets — with or without
`zikzak_inappwebview` present.

## Reproduction

1. `flutter run -d macos` literally any Flutter app with an `AppBar` (or any
   widget with `elevation`/`shadow`) on macOS.
2. Watch the debug console: the `CATransformLayer … will have no effect`
   warnings appear immediately, independent of any WebView usage.

(Marked automated; this is a framework-level behavior, not specific to this
repo. The zuraffa_browser demo happens to trigger it via its standard Material
`AppBar`/`InputChip` UI.)

## Suspected Code Paths

- Flutter engine / macOS embedder (`flutter/shell/platform/darwin/macos`,
  `flutter/impeller` + `CA*` compositing) — the code that builds
  `CATransformLayer` and assigns shadow properties to it. NOT in this repo.
- `zuraffa_browser/lib/main.dart:219` (`AppBar`) and `:244` (`InputChip`) —
  these are the Flutter Material widgets whose elevation causes the engine to
  emit the warning. They are app UI, not zikzak_inappwebview code.
- `zikzak_inappwebview` — **no** code path here sets shadow properties or
  creates `CATransformLayer`s; the WebView is embedded as a native AppKit
  platform view. There is no zikzak source line that can produce this message.

## Root Cause Hypothesis

Misattribution. The warning is generated by the Flutter macOS embedder when it
composites Flutter Material widgets that have shadows onto transform-only
Core Animation layers. It has nothing to do with `zikzak_inappwebview` —
removing the WebView entirely still reproduces it. Confidence: **high**.

## Proposed Remediation

**Do NOT file or fix this in zikzak_inappwebview** — it is not a zikzak defect.
Options if the noise is genuinely unbearable in the demo:

- Preferred (app-side, trivial): reduce/disable elevation on the offending
  Material widgets in `lib/main.dart` (e.g. `AppBar(elevation: 0)`,
  `InputChip` with no shadow), or wrap them so Flutter doesn't emit shadow
  layers. This is a cosmetic app tweak, not a library fix.
- Accept it: it is harmless and upstream Flutter's responsibility. There is an
  open class of Flutter macOS "shadow on transform layer" warnings that only
  the Flutter team can fully silence.

**Files likely to change** (only if you choose the app-side cosmetic route):
- `zuraffa_browser/lib/main.dart`

**Tests to add or update**: none — there is nothing to lock in here.

## Risks & Considerations

- Treating this as a zikzak_inappwebview bug would be a waste of effort: the fix
  (if any) lives in the Flutter engine, which is out of scope for this library.
- Suppressing via `NSSetLog`/OSLog filtering is possible but masks real signal
  and is not recommended.

## Open Questions

- None. This is console noise, not a functional defect.
